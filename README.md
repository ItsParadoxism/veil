# Veil

**Private communication. Nothing more.**

Veil is an experimental terminal-native, invite-only encrypted chat for Linux. A relay routes and persists ciphertext; message plaintext and session keys stay on clients.

## What works

- Permanent username backed by an Ed25519 identity
- Offline recovery secret generation and identity key replacement protocol
- One encrypted stream per invite-only session
- Signed and replay-limited relay requests
- XChaCha20-Poly1305 message encryption on the client
- Persistent ciphertext history and history synchronization
- Limited-use and expiring invites
- Self-hosted relay with native TLS or a TLS reverse proxy
- Linux `amd64` and `arm64` releases

This is an early v0.1 foundation, not an audited messenger. Do not rely on it for high-risk communication yet. Key rotation, moderation, encrypted files, multi-device support, traffic-analysis resistance, and an external security audit remain future work.

## Quick start

Install the latest Linux client without Go or sudo:

```bash
curl -fsSL https://raw.githubusercontent.com/422dev/veil/main/install.sh | sh
```

Then create or join a session:

```bash
veil claim alice
veil create
veil
```

The installer supports Linux `amd64` and `arm64`, verifies the release SHA-256 checksum, and installs to `~/.local/bin`. To install the self-hosted relay too:

```bash
curl -fsSL https://raw.githubusercontent.com/ItsParadoxism/veil/main/install.sh | sh -s -- --relay
```

### Build from source

Requires Go 1.24 or newer.

```bash
go build -o bin/veil ./cmd/veil
go build -o bin/veil-relay ./cmd/veil-relay

./bin/veil-relay -listen 127.0.0.1:7443 -data ./veil-relay-data.json
```

In another terminal after building:

```bash
./bin/veil claim alice
./bin/veil create
./bin/veil
```

`veil create` prints an invite. On another machine or with a separate local state file:

```bash
VEIL_STATE=/tmp/veil-bob.json ./bin/veil claim bob
VEIL_STATE=/tmp/veil-bob.json ./bin/veil join 'veil+http://127.0.0.1:7443/SESSION#TOKEN.KEY'
VEIL_STATE=/tmp/veil-bob.json ./bin/veil
```

The `veil+http://` form exists only for localhost development. Production invites use `veil://`, which resolves to HTTPS.

## Commands

```text
veil claim [--relay URL] <username>
veil recover [--relay URL] <username> <recovery-secret>
veil create [--relay URL]
veil join <invite>
veil chat [session]
veil send [--session ID] <message>
veil invite [--session ID] [--uses N] [--expires 10m]
veil who [--session ID]
veil sessions
veil status [--relay URL]
```

Inside chat: `/help`, `/who`, `/invite`, `/clear`, `/leave`.

The client state defaults to the OS user configuration directory and is written with mode `0600`. Override it with `VEIL_STATE`. Override the default relay with `VEIL_RELAY`.

## TLS deployment

The relay can terminate TLS directly:

```bash
veil-relay -listen :7443 -data /var/lib/veil/data.json \
  -tls-cert /path/fullchain.pem -tls-key /path/privkey.pem
```

Alternatively, bind the relay to localhost and place it behind a TLS reverse proxy. Plain HTTP should never cross an untrusted network: TLS protects request metadata and the identity/invite operations even though message bodies are end-to-end encrypted.

## Security model

- Identity ownership is proved through signed requests; the relay stores only username-to-public-key mappings.
- The session key is generated by the creating client and delivered in the URL fragment of an invite. The invite token is separately hashed by the relay.
- Message ciphertext is authenticated with sender/session/message metadata as associated data.
- The relay can still observe IPs, connection timing, session membership, message size, and timing. Veil does not claim anonymity.
- Current group-key distribution is appropriate only for the prototype. Removing a member does not yet revoke their session key; membership changes require authenticated key rotation before moderation is security-complete.
